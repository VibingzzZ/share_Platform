# 组织工作台首版设计

## 目标

构建一个面向组织内部成员的内容工作台，集中展示组织资源、开发博客和 AI 产品实验，同时允许每位成员保存自己的页面布局偏好。首版优先保证浏览、查找和持续更新的效率，并为后续对外开放、真实身份认证和对象存储预留边界。

## 技术方案

- 后端：Go，提供 REST API。
- 数据库：PostgreSQL。
- 前端：独立的 Web 单页应用，通过 API 获取内容和用户布局。
- 文件：组织自建文件先放在仓库 `resources/` 目录，数据库只保存元数据和相对路径；后续可替换为对象存储适配器。
- 配置：环境变量提供数据库连接、服务端口和资源目录。

## 数据模型

### users

保存内部成员基本信息和角色。角色首版为 `member` 与 `admin`，认证实现可先使用开发环境的请求头/演示用户适配器，接口不绑定具体身份供应商。

### resources

保存资源标题、类型、标签、描述、链接或文件相对路径、作者及发布时间。资源类型包括文档、代码、模板、工具和其他，支持按类型与标签筛选。

### posts

保存博客标题、摘要、正文、封面、标签、作者、发布状态和时间。公开查询只返回已发布内容，管理员接口可管理草稿。

### ai_products

保存产品名称、简介、产品链接、封面、标签、状态和排序。用于展示 Dify 及其他组织实验产品。

### user_layouts

每个用户一条当前布局记录，使用 JSONB 保存模块顺序、显隐、密度和主题。例如模块 key 为 `overview`、`resources`、`posts`、`ai-lab`；布局接口对未知模块做校验并保留向前兼容字段。

## API 边界

- `GET /api/v1/dashboard`：返回首页概览数据及最近资源、文章和 AI 产品。
- `GET /api/v1/resources`、`GET /api/v1/posts`、`GET /api/v1/ai-products`：分页、筛选和详情查询。
- `GET /api/v1/layout`、`PUT /api/v1/layout`：读取和保存当前用户布局。
- `POST/PUT/DELETE /api/v1/admin/resources`、`posts`、`ai-products`：管理员内容维护。
- `GET /api/v1/health`：服务健康检查。

错误响应统一返回 JSON，包含稳定的错误 code 和面向用户的 message；列表接口统一返回 `items`、`page`、`pageSize` 和 `total`。

## 前端信息架构

首页是内部工作台，不做营销型首屏。顶部提供组织身份、全局搜索和 DIY 入口；主体由可拖拽/排序的模块组成：组织概览、最近资源、开发日志、AI 实验室。资源、文章和产品使用密集但易扫描的列表/卡片呈现，详情可在同页抽屉打开。DIY 抽屉允许模块显隐、顺序调整、紧凑/舒适密度和明/暗主题，并在保存后调用布局 API。

## 权限与演进

普通成员可读取已发布内容并保存自己的布局；管理员可维护内容。首版认证采用可替换的用户解析接口，避免把页面和 API 绑定到具体登录系统。后续可增加组织空间、评论、版本历史、全文搜索、对象存储和对外发布状态。

## 验证策略

- 后端单元测试覆盖布局校验、分页筛选、权限中间件和健康检查。
- API 集成测试使用临时 PostgreSQL 数据库或 Docker Compose 服务，验证迁移、种子数据和主要读写链路。
- 前端验证首页加载、筛选、DIY 保存/恢复和移动端布局。
- 提供本地启动文档、环境变量示例和数据库迁移命令。
